# Q1
- 3-6 речень: які структури Redis і команди обрали, який ключ дедуплікації і чому.

Було обрано Redis Streams, так як вони дозволяють імітувати роль exchanger-a, тримати необроблені запити в окремому пулі та налаштувати автоматичну дедуплікацію. Команди:
XGROUP CREATE ... MKSTREAM, XADD, XREADGROUP, XACK, XPENDING, XCLAIM. Ключ дедуплікації - повний payload запиту, так як дублікати ідентичні побайтово, повтор статусу, але з іншим timestamp це окрема подія, а не дублікат.

- Коротко, що станеться, якщо под впаде на кожному кроці вашого обробника.

Якщо под недоступний - таймаут або розрив зʼєднання(в будь-якому випадку retry після 5с). На етапі обробки запиту клієнт отримає статус 500 при помилці в XADD. На етапі обробки запиту в черзі - передача на етап пошуку "завислих" запитів і їх обробка. Після 5 спроб - запис поміщається в dead-letter стрім і забирається з пулу.
Якщо запис був поміщений в БД але впав на етапі XACK, відбудеться ретрай - необхідно налаштувати перевірку унікальності записів в самій БД

- Що робить обробник, коли Redis недоступний: пропускає події чи відмовляє, і чому саме так для цього сценарію.

Відмова зі статусом 500. Допоки Redis недоступний, подія не може бути збережена для подальшої обробки. Віддати статус 200, не записавши дані в Redis означає втратити подію.

- Статуси можуть прилітати не в тому порядку (completed раніше за accepted). Як би ви це врахували, без коду.

Запис в БД без змін. При отримані даних за поїздкою сортувати за пріоритетністю статусу.(можливо додатковий лічильник на кшталт `sequence` від відправника і сортування по ньому)

# Q2
- Пам'ять подів росте, OOM за кілька діб.

```
const history = flow.get('history') || [];
history.push(msg.payload);
flow.set('history', history);
```

Причина: ніде нема очиски history. З часом розмір масиву розростається, що спричиняє OOM.
Рішення: встановити ліміт на розмір history, або зберігання цього поля поза середовищем Node-RED (наприклад Redis)

- Частина запитів дублюється далі по флоу, в логах трапляються помилки на http response.

```
node.send(msg);
return msg;
```

Причина: `node.send(msg)` дублює output function-вузла, відповідно, логіка дублюється для всіх вузлів нижче по флоу. Помилки на http response стаються через вже виконаний callback. Другий не очікується.
Рішення: прибрати `node.send(msg)`;

- Частина документів не доїжджає в базу, а в логах при цьому майже порожньо, клієнт іноді отримує таймаут

Причина: відсутній catch-вузол. Помилки не відловлюються, відповідь на запит не надходить. Запити, які "впали" ніяк не обробляються і губляться.
Рішення: додати catch-вузол. Повертати 500 помилку, логувати її, організувати retry логіку для запитів, які впали.

- stats.processed стабільно менший за реальну кількість оброблених запитів.

Причина:
```
const stats = global.get('stats') || { processed: 0 };
stats.processed = stats.processed + 1;
global.set('stats', stats);
```

У випадку перезапуску пода через OOM значення global контексту скидається, звідси може бути заниження показника відносно реальної цифри. Значення global контексту поширюється на конкретний под, якщо потрібна загальна кількість оброблених запитів(на всіх подах), ця цифра не буде правдивою.
Рішення: обрахунок кількості оброблених запитів поза Node-RED.

## Потенційні проблеми
```
const stats = global.get('stats') || { processed: 0 };
stats.processed = stats.processed + 1;
global.set('stats', stats);
```

Потенційний race condition, якщо подібна операція над полем виконуєтсья в асинхронному режимі.

# Q3
- Агрегація. Pipeline для сценарію A: кількість completed по кожному user_id за 30 днів.

```
[
  { $match: { status: "completed", created_at: { $gte: {{date}} } } },
  { $group: { _id: "$user_id", trips: { $sum: 1 } } },
  { $match: { trips: { $gte: {{N}} } } }
]
```

- Індекси. Які закладете і під який сценарій, з урахуванням розміру колекції й темпу запису. Чого б свідомо не робили.

Partial index(index A+ index B) на статус "completed" дозволяє зменшити кількість даних для доступу при виконанні агрегації.
Compound index(A) by created_at+user_id
Compound index(B) by user_id+created_at
Не робити індекси на окремі поля(created_at, user_id), так як без обох полів в індексі потрібен буде fetch для кожного документа.

- Кеш. Як тримали б значення для сценарію B у Redis: структура ключів, TTL, що робите при новій події.

Ключ: trips30:{{user_id}}, TTL - 15 хв + jitter. Інвалідація кеш при отриманні нової події за статусом "completed".

- Вікно 30 днів ковзне: події "випадають" з нього без жодного запису. Як ваш кеш лишається коректним, і яка його похибка, якщо ви її допускаєте.

Кеш наближений. Значення живе до ~18 хв (TTL 15 хв + jitter), нові completed-події інвалідують ключ, але випадання старих поїздок з вікна кеш не бачить. Тому можливе лише завищення, і лише для поїздок, що випали за час життя ключа: для користувача з 10 поїздками це ≈ 0.4% запитів на +1. Це зачіпає лише користувачів рівно на порозі N і лише на кілька хвилин.

- Грубо оцініть обсяг пам'яті Redis під ваш кеш для 20 млн користувачів.

Один ключ ≈ 90-100 Б (ключ ~24 + хеш-таблиця й redisObject ~40 + запис TTL ~32 + округлення ~10).
20M користувачів × ~95 Б ≈ 1.9 ГБ, із запасом на фрагментацію (×1.2) ~2.3 ГБ.
Реально в кеші лише ті, кого читали за TTL (20-30%): ~0.5 ГБ.
